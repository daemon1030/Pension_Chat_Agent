연금 상담 AI

연금 제도 문서와 상품 투자설명서를 근거로 답하는 상담 보조 시스템입니다. 숫자와 가입 가능 여부는 DB로 확인하고, 복잡한 설명과 예외는 문서 검색(RAG)으로 찾아 AI가 이해하기 쉬운 답변으로 정리합니다.

한눈에 보기질문 처리문서 전처리DB·RAG추천 알고리즘상황별 대응현재 범위

한눈에 보기

TL;DR. 이 시스템은 단순히 AI에게 답을 맡기지 않습니다. 질문의 종류를 구분하고, 추천이라면 계좌 유형과 위험 선호를 확인한 뒤 DB로 후보를 좁힙니다. 이어서 관련 문서 근거를 검색하고, 그 근거에 바탕을 둔 답변과 출처를 제공합니다.
1. DB

정확한 조건 확인

가입 가능한 계좌, 위험등급, 판매 채널처럼 비교 가능한 값으로 명백히 맞지 않는 상품을 제외합니다.

2. RAG

문서 근거 검색

세제·수령 규정, 상품 전략, 수수료, 환매 조건처럼 설명이 필요한 원문을 찾습니다.

3. AI

상담 언어로 설명

사용자 질문과 검색 근거를 연결해 자연스럽게 설명합니다. 근거가 없으면 추측하지 않도록 지시합니다.

현재 구현 기준 CLI 기반 MVP이며 PostgreSQL·pgvector, HyperCLOVA, LangGraph 흐름이 연결되어 있습니다. FastAPI, 세션 복원, 완전한 grounding 검증과 범용 Rule Engine은 향후 확장 항목입니다.

아래 상자를 클릭하면 해당 구현 파일, 역할, 핵심 코드를 볼 수 있습니다.

사용자·입력처리 단계외부 서비스·저장소데이터

문서는 답변 전에 어떻게 준비되나요?

원본을 단순 요약하지 않고, 나중에 원문 페이지까지 되돌아갈 수 있도록 Section(의미 단위)과 메타데이터를 남기는 방식입니다.

일반 제도·규정 문서

PDF, Word, Excel, PowerPoint를 페이지·슬라이드·시트 단위의 공통 JSON으로 변환합니다.
원문에 명확한 제목, FAQ, 예외, 숫자만 보강합니다. 확신할 수 없으면 검토 대상으로 남깁니다.
각 Section을 FACT_AND_RAG, RAG_ONLY, EXCLUDE로 분류합니다.
RAG 대상은 줄 경계를 유지하며 최대 1,200자 단위로 나누고, 문서·페이지·Section 출처를 붙입니다.

상품 투자설명서

상품 클래스, 위험등급, 계좌 가능 범위, 수수료 등 구조화된 항목의 형식과 일관성을 검사합니다.
가입 가능 여부를 판단하는 상품 클래스 DB와 상품 설명 근거를 찾는 Product RAG로 분리합니다.
같은 상품의 여러 판매 클래스는 class_id로 구분하되, 공통 product_id를 유지합니다.
왜 두 경로로 나누나요? “IRP에서 가입 가능한가”처럼 정확한 값 비교는 DB가 잘하고, “중도 환매 시 어떤 유의사항이 있는가”처럼 예외가 많은 자연어 설명은 RAG가 잘합니다.

DB와 RAG에는 무엇을 저장하나요?

상품 클래스 DB: 정확한 필터

실제 가입 단위인 클래스별로 한 행을 저장합니다. 추천 전 후보를 좁히는 데 사용합니다.

대표 필드용도
eligible_account_types연금저축·IRP·퇴직연금 가입 가능 여부
risk_grade안정·균형·공격 성향과 위험등급 비교
sales_channel온라인·오프라인·온라인슈퍼 조건
asset_type, fee, redemption향후 선택 조건과 비교할 수 있는 상품 특성

RAG 청크: 설명의 출처

숫자 벡터만 저장하지 않고 본문과 출처를 같이 저장합니다.

대표 필드용도
contentAI에 전달할 원문 근거
document_id, title문서 추적
page_start, section_id사용자에게 보여줄 출처
product_id특정 상품과 근거 청크 연결
embedding (1024차원)질문과 의미가 가까운 청크 검색
상품 클래스: “가입 가능한가?”를 판단\nRAG 청크: “왜 이 후보인지, 어떤 유의사항이 있는가?”를 설명\n\n예시: IRP + 안정추구\n→ DB: IRP 가입 가능 + 위험등급 5~6인 클래스 조회\n→ RAG: 남은 상품의 위험·전략·수수료·환매 관련 원문 검색

현재 추천 알고리즘

현재 코드는 다음의 재현 가능한 순서로 추천 근거를 만듭니다.

필수 조건 확인: 계좌 유형과 위험 선호가 없으면 필요한 정보만 역질문합니다. 투자 기간과 목적은 선택 정보입니다.
DB 필터: 판매 중, 해당 계좌에서 가입 가능, 위험등급 범위 일치, 선택적으로 판매 채널 일치 조건을 SQL로 확인합니다.
중복 제거: 클래스 단위 결과를 product_id로 묶어 같은 상품이 RAG 후보에 반복되지 않게 합니다.
상품별 근거 검색: 질문을 임베딩하고, DB 후보 상품의 청크만 코사인 유사도로 검색합니다. 상품별 최대 두 청크를 보존합니다.
현재 순위: 첫 근거 점수 + 두 번째 근거 점수의 20%로 정렬해 서로 다른 상품 최대 다섯 개를 LLM에 전달합니다.
최종 설명: AI가 후보와 근거를 읽어 비교 설명을 만들고, Pydantic이 정해진 JSON 응답 형식을 확인합니다.
현재 상품별 근거 점수\n= 첫 번째 RAG 유사도 점수 + (두 번째 RAG 유사도 점수 × 0.2)\n\n의미: 문서가 질문과 더 관련 있어 보이는 상품을 먼저 설명에 넣되,\n같은 상품의 많은 청크가 결과를 독점하지 않도록 최대 2개까지만 사용
향후 AI 추천 고도화 방향. 현재는 RAG 유사도로 최대 5개를 코드가 먼저 고릅니다. 향후에는 DB 필터를 통과한 모든 고유 상품(현재 데이터 기준 2~15개)의 카드와 근거를 AI에 전달해, AI가 사용자 목적에 맞춰 3~5개를 비교하도록 확장할 수 있습니다.

다양한 질문 상황에 대한 대응

사용자 상황시스템 동작중요한 원칙
“IRP에서 안정적인 상품 추천”계좌·위험 조건 확인 → DB 후보 → Product RAG → 근거 기반 설명추천 전 명백한 가입 불가 상품 제외
“연금저축 세액공제 조건은?”정책 RAG에서 관련 제도 문서 검색 → 출처 답변상품 추천 경로를 억지로 사용하지 않음
“연금 추천해줘”계좌 유형과 위험 선호만 역질문사용자 조건을 추측하지 않음
조건에 맞는 상품 없음NO_MATCHING_PRODUCT 안내존재하지 않는 상품을 만들지 않음
문서 근거가 없음NO_GROUNDED_CONTEXT 안내확인되지 않은 사실을 답하지 않음
연금과 무관한 질문OUT_OF_SCOPE 안내서비스 범위를 명확히 안내

현재 구현 범위와 다음 단계

현재 구현됨

  • 원본 문서 → Section 기반 JSON → RAG 청크 전처리
  • 상품 클래스 DB와 Product RAG 분리
  • PostgreSQL·pgvector 벡터 검색
  • 질문 의도 분기, 정보 부족 역질문
  • 상품 조건 필터, 근거·출처가 있는 답변
  • HyperCLOVA JSON 출력 형식 검증·재시도

확장 예정·한계

  • 현재는 단일 턴이며 세션 기억을 복원하지 않습니다.
  • 짧은 문장에서는 LLM이 계좌·위험 조건을 놓칠 수 있어, 표현 사전 또는 튜닝이 필요합니다.
  • 상품 RAG 청크는 주제별로 짧고, 500~1,000자 상품 프로필 계층은 아직 없습니다.
  • 답변 문장 자체가 모든 근거를 정확히 따르는지 검사하는 grounding 검증은 아직 없습니다.
  • FastAPI API, 고급 입력/출력 Guard, 세제 계산 Rule Engine은 아직 연결되지 않았습니다.
추천 MVP의 다음 우선순위: (1) “IRP에서 안정적인” 같은 핵심 표현 보완 추출, (2) 대표 질문 시나리오 회귀 테스트, (3) 후보 전체를 AI가 비교하는 추천 방식 검토, (4) 실패 사례가 쌓인 뒤 조건 추출·후보 준수 행동 중심 튜닝.
